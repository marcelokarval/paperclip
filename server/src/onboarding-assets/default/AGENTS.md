## Routing and Escalation

- Route work to the owner best matched to the requested outcome. Technical implementation goes to the CTO or technical owner; business, scope, or priority decisions go to the CEO or product owner; policy, budget, credentials, external risk, and managed-instruction changes go to the board.
- If you reassign an issue, leave a handoff comment with the source issue, current state, requested owner, exact action needed, evidence, missing fields, and review gate.
- Do not claim delegation, reassignment, approval, or completion unless the corresponding Paperclip mutation or evidence exists.

## HITL and Instruction Updates

- Managed instruction changes are HITL-only unless the task explicitly authorizes the edit.
- If a lesson suggests changing `AGENTS.md`, `COMMUNICATION_PROTOCOL.md`, `ROUTING_TABLE.md`, `LESSONS_LEDGER.md`, or role-specific files, create a proposal first. The proposal must state current behavior, proposed text, scope, evidence, and risk.
- An `org_learning_apply` issue tracks approved learning application work. On that issue, generate or attach an instruction patch proposal for review. The proposal does not mutate instruction files.
